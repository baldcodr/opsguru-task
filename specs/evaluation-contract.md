# CloudNova Evaluation Contract

Status: Approved for implementation  
Version: 1

## 1. Purpose

The evaluation suite proves deterministic business correctness, source citation integrity, routing behavior, interface parity, and honest limitations. It separates offline release gates from optional hosted-model observations.

## 2. Evaluation Principles

1. Exact financial and population results are more important than prose similarity.
2. Expected values are generated by an independent reference oracle that does not import application modules.
3. Golden values are frozen with the source CSV SHA-256 and contract versions, reviewed, and committed.
4. Application code never rewrites its expected values during tests.
5. Every metric assertion checks intermediary counts and complete evidence membership, not only the headline number.
6. Offline CI never requires a hosted model, network access, or secret.
7. Expected limitations are reported explicitly as `XFAIL`; a separate assertion verifies the product's honest refusal behavior.

## 3. Artifacts

- `evals/golden.json`: frozen dataset fingerprint, contract versions, exact metric outputs, contribution IDs/source rows, and quality counts.
- `evals/cases.json`: natural-language cases, expected intent, expected result selector, and evaluation mode.
- `evals/reference_oracle.py`: standalone golden generator using only standard-library parsing and the approved contracts; it must not import `app`.
- `evals/run.py`: human-readable pass/fail/XFAIL runner over the public application service.
- `tests/`: focused unit and interface contract tests.

Regenerating `golden.json` is a deliberate maintainer action. CI fails when its recorded CSV SHA-256 differs from the current source.

## 4. Pass Categories

- `PASS`: all mandatory assertions succeed.
- `FAIL`: a required supported behavior is wrong or unavailable.
- `XFAIL`: the case is intentionally unsupported for a documented data limitation.
- `XPASS`: an expected limitation unexpectedly returns a numeric answer; this fails CI until the contract is reviewed.
- `SKIP`: only permitted for the opt-in hosted-provider smoke test when credentials are absent.

Release requires zero `FAIL` and zero `XPASS`. The declared `XFAIL` is required and appears in the summary.

## 5. Golden Metric Cases

### EVAL-001: 2024 Recognized Revenue

- **Question:** “What was our total recognized revenue in USD for paid invoices in 2024?”
- **Expected intent:** `recognized_revenue_2024`
- **Assertions:** exact net/paid/refund USD values, paid/refunded counts, ambiguity/anomaly counts, and complete contribution set from `BUS-001`.
- **Acceptance:** deterministic template and hosted synthesis modes have identical structured values and evidence.

### EVAL-002: Regional Average MRR

- **Question:** “Which region has the highest average MRR per account?”
- **Expected intent:** `regional_average_mrr`
- **Assertions:** exact regional ordering, numerators, denominators, averages, winner, churn exclusions, and snapshot evidence from `BUS-002`.
- **Acceptance:** annual and monthly snapshots use the same list-price MRR formula.

### EVAL-003: Refunds

- **Question:** “How much have we given back in refunds?”
- **Expected intent:** `refunds_total`
- **Assertions:** exact positive amount given back, negative revenue impact, count, currency breakdown, anomaly count, and complete evidence from `BUS-003`.

### EVAL-004: Plan Churn

- **Question:** “What's the churn rate among Enterprise accounts vs Starter?”
- **Expected intent:** `plan_churn_comparison`
- **Assertions:** exact unique-account numerators, denominators, rates, percentage-point difference, unknown exclusions, and snapshot evidence from `BUS-004`.

### EVAL-005: Top Accounts and CSAT

- **Question:** “List the top 5 accounts by revenue, and flag any with CSAT <= 2.”
- **Expected intent:** `top_accounts_revenue`
- **Assertions:** exact five-account order, IDs, latest names, revenue, contributing counts, CSAT values/statuses, tie-breaks, and evidence from `BUS-005`.

### EVAL-006: Payment Exposure

- **Question:** “How many invoices are stuck in pending/failed and what's the exposed $?”
- **Expected intent:** `payment_exposure`
- **Assertions:** exact overall/per-status counts and USD totals, negative anomaly count, and complete evidence from `BUS-006`.

## 6. Required Expected Limitation

### EVAL-XFAIL-001: Monthly Cohort Churn

- **Question:** “What was our monthly churn rate throughout 2024?”
- **Expected numeric evaluation:** `XFAIL`
- **Reason:** the ledger has a current `churned` flag but no churn date or historical active-state intervals, so monthly denominators and churn events cannot be reconstructed.
- **Guardrail assertion:** the service must return intent `unsupported_metric`, no numeric churn result, and an explanation naming the missing churn date/history. Returning an estimate is `XPASS` and fails release review.

## 11. Optional Live Evaluation

`LIVE-001` runs only when explicitly enabled and configured with an OpenAI-compatible provider. It verifies availability, bounded latency capture, and that the answer does not contradict immutable structured fields or citation IDs. Exact wording is never a release assertion, and absence of credentials is `SKIP`, not failure.

## 12. Human-Readable Eval Output

`python -m app eval` prints one line per case and a final summary:

```text
PASS  EVAL-001  recognized revenue values and evidence match
XFAIL EVAL-XFAIL-001  monthly churn requires missing churn dates
...
Summary: 0 failed, 1 expected limitation, N passed
```

The command exits 0 only with zero `FAIL` and zero `XPASS`.

## 14. Release Acceptance

- Golden file fingerprint equals the supplied CSV.
- EVAL-001 through EVAL-006 pass with exact structured values and evidence.
- EVAL-XFAIL-001 is reported as expected and its refusal guardrail passes.
- No required test is skipped.
- Optional LIVE-001 status is reported separately.
- Test output and known limitations are summarized honestly in README.
